# Governance Engine v0.4 kick-start

## First slice landed

This slice establishes three control-plane primitives:

1. `governance/assessment_identity.py` — immutable assessment fingerprint over model, git SHA,
   retrieval configuration and load-bearing governance artefacts.
2. `governance/register_checks.py` — deterministic change-register integrity checks.
3. `governance/release_gate.py` — model-release gate against stored evaluation results.

It also removes duplicate rows from `governance/tickets.csv`, marks currently uncovered critical
controls as explicitly `human_only`, and adds unit tests in `tests/test_v04_governance.py`.

## Deliberate remaining blockers

The kick-start does **not** claim v0.4 readiness. The existing register still needs reconciliation
against all WB-019..WB-030 references in the repository, the six currently human-only critical controls need
formal assurance decisions, and the current llama3.2 evaluation fails the proposed release gate.

Run:

```bash
python -m pytest -q tests/test_v04_governance.py
python governance/link_check.py
```

The next implementation slice is requirement semantics: fully operationalise the eight critical
MAS controls before changing the assessor prompt/model.

## Rubric and label governance

Run `python eval/label_governance.py` before evaluating a model. It checks obvious rubric/label
contradictions, justification quality, and whether the diagnostic corpus has at least five examples
of each sufficiency class. Distribution readiness is deliberately separate from label correctness:
a thin class is a corpus-design problem, not a reason to relabel a case.

## Structured Challenge Reasoning (v0.4)

`Challenge My Read` now returns a governed reasoning structure rather than a flat list of questions:

`observation → evidence_basis → requirement_basis → knowledge_basis → inference → challenge → recommended_action`

Each challenge also has `severity` and `confidence`. The UI shows these fields separately so the reviewer can distinguish facts, requirement interpretation, advisory precedent, and the Challenger's inference. The Challenger still cannot produce or change a rating.

The `knowledge_basis` field must reference only memory IDs actually retrieved for the challenge. This prevents the model from inventing precedent references.
