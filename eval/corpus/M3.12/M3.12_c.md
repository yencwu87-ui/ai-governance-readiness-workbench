# Model Deployment Change Procedure — Target Operating Model

Data Science Platform | Change Management workstream
Version 0.9 — **for review, not yet in effect**
Author: R. Menon, Platform Engineering Lead
Last updated: 26 February 2026

---

## Background

Model deployments currently follow the general application change procedure, which was
written for release trains and does not describe retraining, rollback of a model version,
or the champion/challenger cutover pattern. This document sets out how change management
will work for the model-serving platform once the platform migration completes in Q4 2026.

It has been reviewed within Platform Engineering and shared with the Change Manager for
comment. It has not been through Change Advisory Board endorsement and is not yet the
governing procedure for any deployment.

## Scope

All changes to models deployed on the model-serving platform, including new model
versions, retraining deployments, feature pipeline changes, threshold or cutoff
adjustments, and decommissioning.

## Change types

| Type | Definition | Approval route |
|---|---|---|
| Normal | Planned model version or config change | CAB, minimum 5 working days lead |
| Standard | Pre-approved retraining on unchanged features and pipeline | Automatic, post-hoc notification |
| Emergency | Change required to restore service or prevent customer harm | Duty manager at implementation, CAB ratification within 2 working days |

The standard-change category is new and will require CAB to pre-approve the retraining
pattern. That submission has not been prepared.

## Controls to be applied

Once effective, every production change will be expected to evidence:

- CAB or duty manager approval recorded before the first production action
- an implementation plan with named implementer, steps and rollback
- privileged access obtained through PAM against the change number, with no use of
  standing accounts
- session recording retained for the duration of the privileged session
- post-implementation verification comparing production state to the approved plan
- a freeze exemption approved by the accountable MD where the change falls in a declared
  freeze window

## Freeze windows

The platform will observe the group release freeze calendar. Exemption authority sits with
the accountable MD. The current procedure does not distinguish freeze authority from
ordinary change authority and this has caused confusion; the intent is to make it explicit.

## Implementation plan

| Milestone | Target |
|---|---|
| Change Manager review complete | March 2026 |
| CAB endorsement of the procedure | Q3 2026 |
| Standard-change pattern submitted for pre-approval | Q3 2026 |
| Procedure effective, aligned to platform migration | Q4 2026 |
| First quarterly change assurance review under this procedure | Q1 2027 |

## Open points

- Whether threshold adjustments are a change or a business parameter update. Data Science
  argue the latter. Unresolved.
- Whether the standard-change category can apply where retraining shifts the population
  materially. No test proposed yet.
- Session recording on the new platform hosts — the recording agent is not part of the
  current build image. Raised with Platform Engineering.
- No baseline has been taken of how the current model deployments perform against the
  controls listed above.
